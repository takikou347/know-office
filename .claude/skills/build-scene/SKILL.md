name: build-scene
description: know-office の tasks.md の 1 項目を、要件のシナリオごとに落ちるテストから作り、main にマージするまでの手順
---

1. 読む: 作る機能の knowidea の `services/know-office/docs/04-detail/<番号>-<名前>.md` と、その文書が指す `openspec/changes/<名前>/specs/` の要件。`04-detail/2-routes.md` と `3-data.md` は全文を読まず、使うルートとテーブルの行を grep で引く。書き方の決まりは、触るファイルに合う `.claude/rules/` が読み込まれるので、05-conventions.md を読み直さない
   - 読んだら、作る前に計画を作り、作った者と別のモデルのレビュー担当に「計画のレビュー」として見せ、通ってから作る。並列の時は渡す側が計画を作って通し、作業者に渡す
   - 計画に入れる物: 詳細設計の直し案 (差分か要点。knowidea のブランチで直したなら、それも見せる)、足す `it()` の名前の一覧、書く所ごとの条件 (1 文かバッチか)、外を呼ぶ所 (相手の API の上限、再送で二重にならない形)、費用が出る所 (初期値 off の設定)、定期の確かめで処理を止める所の誤検知の隙 (変更の途中、同時)
2. ブランチを切る。名前は中身の分かる英語 (例: `access-login`)。1 つのブランチに 1 つのタスク ID
3. 要件のシナリオを 1 つ選び、詳細設計の 4 章「テスト」が指す置き場に、シナリオの名前をそのまま `it()` の名前にしたテストを書く。走らせて、思った理由で落ちる事を確かめ、落ちた出力の要点を控える (7 でレビュー担当に添える)
4. ルートを足す、変える時は、先に `apps/office/openapi/v1.yaml` を直す。詳細設計の 1 章から 3 章のインターフェース、データの形、動きと、`v1.yaml` の形のとおりに作り、そのテストを通す。シナリオが残っていれば 3 に戻る
5. 作った後に、計画で決めた詳細設計か `v1.yaml` と違う形になった時は、同じ時に knowidea の詳細設計を直すブランチを切る。要件が変わる時は、このブランチで `openspec/` も直す
6. 通す: `pnpm verify` (画面を変えたら `pnpm verify --e2e`)。落ちた手順は出力の最後だけが出るので、直したらそのファイルだけを走らせ直し (`pnpm --filter <パッケージ> exec vitest run <ファイル>`)、最後にもう一度 `pnpm verify`
7. レビューの前に、`.claude/rules/api.md` と `tests.md` のうち、よく差し戻される物 (書く条件と一緒に書く出来事を 1 文かバッチに入れる、`x-step-up`、外から来た ID とキーと道の形、前の作業トークンの失効、同時と二重と境目と分岐ごとのテスト、外への送信の二重、費用の出口、設計書の直し) を差分に当てて自分で確かめる。tasks.md の項目に印を付け、作った者と別のモデルのレビュー担当 (作ったのが Opus なら `reviewer-alt`、Sonnet なら `reviewer`) に差分と 3 で控えた落ちた理由を見せる。差し戻しなら直して 6 に戻る。待つ間は次のタスクを進める
8. push して PR を下書き (draft) で出す。PR を作る道具が本文に足す帰属の行を、本文を入れ直して消してから、下書きを外す。CI の pr-body は下書きの間は回らず、下書きを外した時に確かめる。CI が通ったら、そのブランチを main へ fast-forward で push し、ブランチを消す

## 並列で進める時

- 触るファイルが重ならないタスク (画面、共通パッケージの判断、ゲートウェイのルートなど) は、`git worktree` の作業者に 1 タスクずつ渡し、同時に進める
- 作業者は push しない。レビュー、PR、main への取り込みは渡した側が行う。後から入れるブランチは main に rebase し、6 からやり直す
- 承認済みで、触るファイルが重ならないブランチが同時に複数ある時は、1 本ずつ CI を待たずに積んで入れる
  1. 前のブランチの上に順に rebase して積む。v1.yaml の版は積む順に上げ直す
  2. 一番上で `pnpm verify` (画面を変えた物があれば `--e2e`) を通し、積んだ所の衝突の解き方と組み合わせを、作った者と別のモデルのレビュー担当にもう一度見せる
  3. 一番上だけを PR にし、本文に積んだブランチの中身をすべて書く。CI はこの 1 つで全部を確かめる
  4. 落ちたら、どのブランチが原因か分かるまで積みを崩し、1 本ずつに戻す
  5. 一番上を main へ fast-forward で push すると下も入る。入れた後に積んだブランチをすべて消す
- `pnpm verify --e2e` は開発サーバーのポートを使うので、同時に流すのは 1 本だけ。ほかは `pnpm verify`
- knowidea の設計書と 2-routes.md は 1 か所で直す。作業者は直す所を報告し、渡した側がまとめて直す
